### Exact failure site (full traceback, captured with the blocker installed)

```
File ".../cadquery/__init__.py", line 11, in <module>
    from .occ_impl.shapes import (
File ".../cadquery/occ_impl/shapes.py", line 21, in <module>
    from vtkmodules.vtkCommonDataModel import vtkPolyData
File "tools/poc/novtk/vtk_import_blocker.py", line 26, in find_spec
    raise ImportError(f"VTK import blocked during TE-001: {fullname}")
ImportError: VTK import blocked during TE-001: vtkmodules
```

This corrects the initial static-analysis hypothesis in `Discovery.md` (which pointed at
`cadquery/occ_impl/exporters/vtk.py`, also unconditional): `shapes.py` is imported earlier in
`cadquery/__init__.py`, so it is the one that actually fails first. Both files import `vtkmodules`
unconditionally; either alone is sufficient to break `import cadquery` without VTK installed.

The raw Build 021 M1 audit trail (`raw-trace.jsonl`) independently corroborates this: it recorded
two distinct `audit-import` attempts for the vtk namespace during the single failing `import
cadquery` call — `vtkmodules.vtkCommonDataModel` (the outer requested name) and `vtkmodules` (the
parent package resolution, where the blocker's `find_spec` actually raised).

## Runtime trace (Build 021 M1 reuse, section 19)

- `python_module_count`: 571, `native_extension_count`: 21, `loaded_library_count`: 0.
- `incomplete`: `True` (expected: the traced process exits via an unhandled `ImportError` during
  the checkpoint script's own startup, before the recorder's `atexit` "end" snapshot logic in
  `run_checkpoints.py` reaches its normal completion path for downstream checkpoints — the `end`
  event and snapshot were still written correctly since they're registered via `atexit`).
- `error`: `None`.
- `vtk_evidence_hits`: `['vtkmodules', 'vtkmodules.vtkCommonDataModel']`.

**Interpretation (important, and non-obvious from the raw numbers alone)**: the M1 recorder's
`audit-import` hook fires for every import *attempt*, blocked or not — `_read_raw()` records it as
`PYTHON_MODULE` evidence regardless of outcome. These two hits mean *"a vtkmodules import was
attempted"* (expected — that's exactly what `VTKImportBlocker` exists to intercept), **not** that
VTK was actually loaded. Whether VTK actually loaded is answered independently by the `sys.modules`
scan above (`[]`) and by the OS-level evidence below, both of which are clean.

Known limitation hit while reusing the M1 dyld parser (`tools/trace_runtime.py:parse_dyld_output`):
this machine's `DYLD_PRINT_LIBRARIES` output format (`dyld[PID]: <UUID> /path`) doesn't contain the
`loaded:` token the regex expects, so it matched 0 of 2222 real library-load lines. Marked
**NOT VERIFIED** for that specific sub-mechanism; not silently treated as a clean result. See
`Experiment.md` for detail.
