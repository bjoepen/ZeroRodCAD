## The central requirement: ONE unsaved-changes decision model

The mandate's own framing (§0/§7/§52): native window close and native application Quit/Cmd+Q must
never implement independent save/discard/cancel semantics. This milestone's entire architecture is
built around one mechanism that makes that true by construction, not by convention.

### Root cause recap (§6, from `BUILD-025-M1-NATIVE-CLOSE-BUGFIX.md`)

Build 025 M1 found and fixed the red close button (a missing `core:window:allow-destroy` WebView
capability). While tracing that bug, M1 also found — but was explicitly scoped not to fix — a
second, separate defect: macOS's *implicit default* menu bar (auto-generated by Tauri because no
custom menu existed yet) wires its "Quit" item to `PredefinedMenuItem::quit`, which — confirmed
directly in the `muda` crate (`muda-0.19.3/src/platform_impl/macos/mod.rs`,
`PredefinedMenuItemType::Quit => Some(sel!(terminate:))`) — routes straight to AppKit's
`terminate:`, bypassing `WindowEvent::CloseRequested` (and therefore the JS unsaved-changes guard)
entirely. `tao` (`tao-0.35.3/src/platform_impl/macos/app_delegate.rs`) implements no
`applicationShouldTerminate:` override, so there was no hook back into Rust/JS before the process
terminated. This is the exact gap this milestone closes.

### The fix: Quit is no longer predefined — it resumes through the same native event the red button already uses

`desktop/src-tauri/src/menu.rs` builds an **explicit** menu (`Builder::menu(menu::build_menu)` in
`lib.rs`, replacing the implicit default entirely — no `PredefinedMenuItem::quit` anywhere in this
codebase, verified by the gate script's own structural check). Its "Quit ZeroRodCAD" item is a
plain custom `MenuItem`; its click handler (`menu::handle_menu_event`) calls
`WebviewWindow::close()`, whose own doc comment states it "emits `WindowEvent::CloseRequested` first
like a user-initiated close request" — confirmed directly against `tauri-runtime-wry`'s dispatcher
(`Message::Window(id, WindowMessage::Close) => on_close_requested(...)`) to be the *literal same
code path* the red close button's native event already produces, not merely a similar one. Tauri's
own `on_window_event` (`tauri-2.11.5/src/manager/window.rs`) applies its existing
`has_js_listener` → `prevent_close()` logic identically regardless of which produced the event, so
`main.ts`'s single `onCloseRequested` handler — and therefore `project_panel.ts`'s `confirmQuit()`,
the one and only unsaved-changes guard, **completely unchanged since Build 025 M1** — is reached
either way. No guard logic exists in Rust at all: `menu.rs` never inspects project/dirty state.

**Result: FIXED IN M4.** Native Quit/⌘Q now shares exactly the same decision model the red close
button already used and Human-Validated in M1 — not a second, parallel implementation kept in sync
by discipline, but the literal same code path, reached from two different native triggers.

### Re-entrancy (§10 of the mandate)

Because Quit and the red button each independently call `WebviewWindow::close()` (producing their
own, independent `WindowEvent::CloseRequested`), two overlapping close attempts — repeated ⌘Q,
⌘Q while the red-close guard is already showing, red close while a ⌘Q guard is active — would
otherwise call `confirmQuit()` twice concurrently, stacking a second Save/Discard/Cancel dialog on
the first. This is handled by a new, small, dedicated module, `desktop/frontend/src/close_flow.ts`
(extracted out of `main.ts`, which has top-level side effects on import and — per this project's
established convention — has never been unit-tested directly; extracting this one piece is
specifically so the safety-critical property is directly tested, not only exercised by the real
app): `createCloseRequestHandler` makes every close attempt that arrives while a decision is
already in flight defer to that *same* in-flight decision (cancelling its own event immediately)
rather than starting a second one. Once a decision fully resolves, the next attempt starts fresh.
Proven directly by `close_flow.test.ts`: exactly one `confirmQuit()` call across up to four
overlapping attempts, no stacked dialogs, and a dedicated test proving the red-close and Quit code
paths are — literally, not just behaviorally — the same handler instance.

## File/View menu routing — no logic duplicated in Rust (§9/§20/§21)

`desktop/src-tauri/src/menu.rs`'s `handle_menu_event` is a router with exactly one special case
(`"quit"` → `WebviewWindow::close()`, above). Every other click is forwarded verbatim as a
`"menu-action"` Tauri event (`{id, checked?}` — `checked` present only for the three visibility
items, carrying the native item's own already-toggled state so the frontend never has to guess or
complement a value). `desktop/frontend/src/native_menu.ts` (new) is the frontend half: it maps each
id to the *exact same* controller method the visible UI already calls —

- File → New/Open/Save/Save As: `project_panel.ts`'s new `triggerNew`/`triggerOpen`/`triggerSave`/
  `triggerSaveAs` — thin wrappers around the *same* `guardThenRun`/`performSave`/`performSaveAs`
  functions the visible buttons' click handlers already call. Each already no-ops safely when the
  action isn't currently valid (mirroring the visible button's own disabled state), so no separate
  enabled-state plumbing was needed for the menu.
- File → Export Model…: `export_panel.ts`'s new `triggerExport`, wrapping the same
  `handleExportClick` the visible button uses.
- View → Reset View: `preview.ts`'s existing `resetView()` directly — no camera logic in Rust.
- View → Instrument Report / Diagnostics: `report_panel.ts`/`diagnostics_panel.ts`'s new `open()`
  methods — the exact same fetch/render/toggle logic the visible toggles already use, not a second
  report/diagnostics implementation or window.

No new Rust command exists for any of these — File/View/Reset-View/Report/Diagnostics all reuse the
existing IPC boundary (`engine_project_*`/`engine_export`/`engine_report`/`app_info`/
`engine_status`/`engine_sidecar_status`, all unchanged since M1-M3) purely by routing through the
same frontend controller methods that already call them.

## Show Body/Rod/Strings — bidirectional native menu ↔ visible checkbox sync (§15/§16/§29)

The mandate's own example: "Body unchecked via menu → Body disappears → visible Body control
reflects hidden state. Body re-enabled via visible control → native menu state reflects visible."
Both directions funnel through exactly one function, `native_menu.ts`'s
`createNativeMenuBridge(...).setLayerVisible`, which (in this order) updates the Three.js scene
(`preview.ts`'s existing `setLayerVisible`, unchanged since M3), reflects the new state into the
visible checkbox (`view_controls.ts`'s new `setCheckboxState` — sets `.checked` directly, which does
not fire a `change` event, so this is a one-way reflection, not a feedback loop), and syncs the
native menu's own checked glyph via a new, narrow Rust command, `set_view_menu_checked`. `main.ts`
wires `view_controls.ts`'s own IO to this same bridge function (via the established
forward-reference pattern `exportPanelRef`/`projectPanelRef`/`reportPanelRef` already use) instead
of directly to `preview.setLayerVisible`, so a visible-checkbox-driven change and a native-menu-
driven change are indistinguishable from that point on — there is exactly one place visibility
ever changes, never two.

Visibility ownership itself did **not** move into Rust (§16 explicitly forbids this) — `preview.ts`
remains the single source of truth; the native menu's `CheckMenuItem`s are a mirror, looked up by id
in the real menu tree (`Menu::get`/`Submenu::get`) each time `set_view_menu_checked` runs, not
cached separately.

`set_view_menu_checked` requires **no new WebView capability**: it is an app-owned command (like
every `engine_*`/`select_*` command already registered), not a plugin command, so it is not
ACL-gated — `capabilities/main-capability.json` names none of the existing app-owned commands
either, confirmed against `desktop-schema.json`, which only gates `plugin:*`-namespaced commands.

## Testing — evidence and its honest limits

- **`close_flow.test.ts`** (new): the actual safety-critical re-entrancy property, tested directly
  — clean/Cancel outcomes, overlapping close attempts producing exactly one guard decision, a
  decision resolving cleanly before the next attempt starts fresh, and an explicit test proving the
  red-close and Quit entry points share one handler instance.
- **`native_menu.test.ts`** (new): the full menu-id → application-action routing table
  (`dispatchMenuAction`), including the three visibility items routing through the shared
  `setLayerVisible` with the native item's own reported checked value, an unrecognized id never
  throwing, and confirmation that `"quit"` never reaches any project/export/preview/report/
  diagnostics action here (it is handled entirely natively).
- **Rust**: `tests/native_menu.rs` (new) proves `handle_menu_event`'s routing for `"quit"` and a
  representative non-quit id complete without panicking against a real `MockRuntime` app with only
  a main window present — the boundary this module's routing logic actually owns.
- **Honest limitation, not a gap papered over**: real *menu construction*
  (`Menu`/`Submenu`/`CheckMenuItem`/`PredefinedMenuItem::with_id`/`::about`, via `muda`) cannot be
  exercised under `cargo test` — confirmed directly, not assumed: `muda::MenuChild` panics with
  "can only be created on the main thread" even with `--test-threads=1`, because `cargo test`'s
  binary never runs on the real, `NSApplication`-registered Cocoa main thread the way a real
  launched GUI app does. This is the identical class of limitation `preview.test.ts`'s own module
  doc comment already documents for `createPreviewController` (no GPU context under jsdom). In its
  place: (a) direct source inspection, encoded as structural checks in
  `scripts/validate-build025-m4.sh` (no `PredefinedMenuItem::quit(...)` call anywhere; the Quit item
  is a plain `MenuItem`; exactly three `CheckMenuItem`s exist, none constructed with
  `checked: false`); (b) a real `cargo tauri dev` launch performed during this milestone's
  implementation, which **does** run on the true main thread, confirming the menu constructs and the
  app runs without a panic/crash; (c) artifact-level proof against the final compiled release
  binary — `strings(1)` search for the menu's own id/event-name string constants and visible labels
  (§42 of the mandate: "do not rely only on source inspection" — see the Abschlussbericht for the
  actual recorded evidence).

## Scope freeze — what M4 deliberately does NOT do

Per the mandate's own §4/§51/§53: no Settings/Preferences, no Recent Files, no file associations, no
Finder/Open-With/Quick-Look integration, no drag & drop, no auto-update system, no signing/
notarization, no PySide6 retirement, no engine/sidecar/protocol redesign. `project.py` and the
domain package (`zerorodcad/`) were not touched.
